The four betsDesign principles

Numbers from state, words from the model

Scores, overs and run rates are read from the match state and passed to Claude. The model explains; it never recalls a number.

Most questions never reach the LLM

"What's the score?" is answered from a template in under 100 ms. Repeated questions hit a cache keyed by state version.

One shared prompt prefix per ball

Every fan's prompt starts with the same system text and the same match snapshot, so prompt caching serves ~78% of input tokens.

The kickoff time is known

The toss is at a published time. Capacity is pre-scaled 30 minutes before, instead of waiting for autoscalers to react.

Deliverable 1Requirements

Functional

  • Ask about the live match in plain language: score, situation, players, rules ("why was that not out?").
  • Streamed answers with an "as of over 14.3" stamp on every live figure.
  • Follow-up questions keep context ("and his strike rate?").
  • Live ticker plus auto commentary for every delivery.
  • Stats questions: head-to-head, career figures, venue records.
  • Situation maths: required run rate, par score, projected total, computed by tools and explained by the model.
  • English, Hindi, Urdu and Hinglish.
  • Suggested question chips that change with the game state.
  • Thumbs up/down and report abuse.

Out of scope: betting or fantasy tips, video clips, payments.

Deliverable 2High-level design

Three planes. The request path answers questions. The live data path turns the feed into one versioned match state. The ticker never touches app servers: the CDN serves it.

LLM path live data path reads, caches, logs failover

One question, end to end

  1. The app sends the question over HTTPS to the edge. The WAF drops bots; the gateway checks the device token and the user's quota (30 questions per 10 min).
  2. The orchestrator runs moderation and intent classification in one cheap pass and normalises the text ("scor?" → score).
  3. About 45% of questions are factual lookups (score, who's batting, required rate). They are filled from a template using the in-memory match state. No LLM.
  4. The rest check the answer cache, keyed by match · state version · language · normalised question. Half hit.
  5. On a miss, identical in-flight questions are coalesced so one Claude call serves all of them. The prompt is built as: system text, match snapshot (both cached), retrieved stats, last 3 turns, question.
  6. The LLM gateway routes to Haiku 5.5, or to Sonnet 5.5 for analysis and "why" questions, and streams tokens back.
  7. A validator checks every number in the answer against the snapshot. On a mismatch the fan gets the template answer, and the case is logged for evaluation.
  8. The answer streams to the fan with its "as of over" stamp, is written to the cache, and is logged to Kafka.

Cross-cuttingScalability, security, failure, maintainability

Scalability

  • Stateless gateway and orchestrator pods scale sideways; all state lives in Redis and Kafka.
  • The CDN absorbs the 2.5M/s ticker load, so a viral moment does not reach app servers.
  • Everything is partitioned by match_id (Kafka key, Redis hash tag), so a parallel match never shares a hot shard.
  • Orchestrators subscribe to state changes and hold the snapshot in memory: zero reads per question.
  • Scheduled pre-scale 30 min before the toss; KEDA on queue depth for the rest.
  • Active-active in two Indian regions behind GeoDNS.

Security

  • Edge WAF, DDoS shield and bot scoring; TLS 1.3; rate limits by IP, device and user.
  • Anonymous signed device token (24 h), upgradable to login. A daily token budget per user stops cost abuse.
  • Prompt injection: fixed system prompt, user text only in the user turn, read-only tools scoped to one match, no secrets or other users' data in context.
  • Input and output moderation tuned for rivalry abuse, communal hate and player harassment; betting tips refused.
  • HMAC-signed feed, schema checks and sanity rules (runs never fall except a flagged correction).
  • API keys in a vault, held only by the LLM gateway; mTLS inside; least-privilege IAM.
  • Pseudonymised logs, 30-day retention, delete on request (DPDP Act 2023).

Maintainability

  • Small services with one job each, and a versioned schema registry for ball events.
  • Prompts and model settings live in a versioned registry and ship through a 5% canary gated by evals.
  • A replay harness re-runs past India–Pakistan feeds at 10× speed, for load tests and answer quality.
  • Golden set of about 500 questions with expected facts per match state, run in CI.
  • OpenTelemetry traces across every hop. Dashboards for feed lag, first-token time, cache hit rate, tokens/min and $/min.
  • Terraform for infrastructure and a runbook for every ladder level.
